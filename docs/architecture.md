# 全体の構成

このリポジトリの作りと、守る決まりと、進め方。指示役も実装役も、作業の前にここを読む。
今のアプリの中身は `docs/spec.md`、決めた理由は `docs/decisions.md`、バトルの作り直しは `docs/battle-plan.md`。

## 1. 三つの層

| 層 | 置き場 | 中身 | 決まり |
|---|---|---|---|
| core | `src/core/`（これから移す） | 番号→キャラ、味の辞書、乱数、バトルの計算 | DOM・時刻・`Math.random`・保存を使わない。入力が同じなら結果も同じ |
| app | `src/` | 画面、演出、音、読み取り、端末への保存 | coreの結果を見せるだけ。勝敗・能力・見た目の仕様をここで決めない |
| worker | `worker/` | 静的配信、商品の中身を調べるAPI | coreを読み込んでよい。商品名・ブランド名は返さない・保存しない |

今のファイルの行き先：

- core へ：`ean.ts` `rng.ts` `creature.ts` `product.ts` `battle.ts`（→ `core/battle/`）
- app のまま：`main.ts` `battle-ui.ts` `render.ts` `morph.ts` `scan.ts` `sfx.ts` `profile.ts` `lots.ts` `gallery.ts`
- `lots.ts` は「いつ新しいロットが出るか」の計算と端末への保存が混ざっている。今は動かさない（ロットの仕様を変えるときに分ける）

決まりは文章でなく仕組みで守る：`src/core/` はDOMの型なしでコンパイルする（`tsconfig.core.json`）。coreで `document` や `localStorage` を書くと `npm run check` が落ちる。

## 2. どこまで一致させるか

| もの | 一致の範囲 | 確かめ方 |
|---|---|---|
| 番号→キャラの仕様・能力（`specFor` `lotLook`） | **どの実装でも完全一致**（Web・Flutter・Worker） | `fixtures/golden.json` |
| キャラの絵（`render.ts`） | 見た目が同じならよい。数値の完全一致は求めない | 見本帳を目で比べる |
| バトルの計算 | **TypeScriptの中で**同じ入力なら同じ結果。別の言語との一致は求めない | テストで操作記録を再生 |

今の `golden.json` には古いバトル計算の5試合（`battles`）も入っている。作り直しの段階2で外す。

バトルを別言語と一致させない理由：相手はいつもCPUで、試合結果を端末どうしで突き合わせる場面がない。将来ランキングや販促企画で不正対策が要るときは、同じTypeScriptのcoreをWorkerで回して検算する。

## 3. データの置き場

- 端末（localStorage）：ロット `barcode-lot:lots:v1`、商品プロフィール `barcode-lot:profiles:v1`、音の設定 `sfx`
- Worker：商品APIの応答を30日キャッシュ。データベースはまだ無い
- D1 を足すのは、端末をまたぐ機能（発見ゲーム、ランキング）を作ると決めたとき。それまで足さない。Supabaseは使わない

## 4. 配信と確認

- `main` へのpush → 本番 https://barcode-lot.shiomizu.workers.dev
- それ以外のブランチ → プレビューURL（Cloudflareの Settings > Build > Branch control で Preview Builds を有効にする。**しおみずの作業**）。実機での確認はこのURLで行う
- **mainに入れるのは、しおみずが確認したあと**

## 5. 終わりの条件（どの作業でも）

1. `npm run check` が通る（型チェック3つ・テスト・ビルド）。PRではGitHub Actionsが同じものを回す
2. 画面を変えたら、スマホ幅（390×844）で録画かスクショを撮り、自分の目で確かめる
3. 変えた内容に合わせて `CLAUDE.md` と `docs/` を直す

## 6. 役割分担

指示役（設計とレビュー）と実装役を分ける。

**指示役がやること**
- 型（インターフェース）を先に書いて固める
- 受け入れテストを先に書く。実装役の仕事は「このテストを通すこと」になる
- 作業を下の形の依頼にして渡す。同じファイルを2人に同時に触らせない
- 出てきた差分をレビューする。見る点：1.と2.の決まり、テストが条件を本当に確かめているか、頼んでいない変更が混ざっていないか

**依頼の形**
```
目的：（1文）
触るファイル：
触らないファイル：
通すテスト：
終わりの条件：npm run check ＋（画面なら録画）
```

**聞かずに決めてよいこと**：変数名・関数の分け方、ファイル内の構成、テストの追加、`TUNE` の仮の数値、演出の細かいタイミング、文言の言い回し

**止まって聞くこと**：`docs/` に書いてある決まりやルールと違うことをしたくなったとき、`fixtures/golden.json` が変わるとき、依存パッケージを足すとき、保存データの形を変えるとき、mainに入れるとき

## 7. あとで見直すこと

- **アプリ版の作り方**：今の方針は「検証後にFlutterで作り直す」。ただしバトルの計算と演出がTypeScriptに積もるほど、作り直しは重くなる。友達テストのあと、Flutterで作り直すか、このWeb版をアプリの殻で包むかを決め直す
- **`main.ts` の分割**：読み取り・値札・棚・画像づくりが1ファイルにある。UIの組み直し（即カメラ全画面・タブ）をやるときに画面ごとに分ける。今は触らない
