# 決めたことの記録

上の「前提」は、しおみずと相談して決まった大きな方針（2026-11-15 までのものは battle-feel ブランチの記録から移した）。
その下は、作業の中で決めたことを新しい順に足していく。形は「決めたこと / 理由 / 捨てた案」。

## 前提：しおみずが大事にしていること

- **一番熱いのは、バーコードを読むところと、それが可愛い・かっこいいキャラになるところ**。ここが主役で、ほかは脇。読む→変身の間に質問をはさまない
- 同じ商品でも1体ずつ違ってほしい。厳選が楽しいし、コラボもしやすいから
- 読むのはバーコードだけにしたい（レシートや別の撮影を必須にしない）
- バトルは「実際に戦ってる感」がほしい。見ているだけは物足りない
- 既存作のパクリと言われたくない
- 開発と運用の費用はできるだけ抑える
- 進め方：先に構成と手順を決めてリポジトリに置き、それを元にエージェントに進めさせる。細かい確認で止まらず、ある程度は自走してほしい

## 前提：決めたこと

| 決めたこと | 理由 |
|---|---|
| 一点は「読んだバーコードの縞がそのままキャラの体になる変身」 | 調べた既存作は「数字→強さ」「1コード→1キャラ」が中心。縞を見た目に使うことで差をつける |
| 品番で姿・名前が全国共通に決まる | 「この商品こいつなの！？」を友達と共有できる。メーカーコラボで「この商品のキャラ」と言える |
| ロットは消費サイクル方式 | バーコードだけでは同じ商品の別の1個を見分けられない。日数を空けて読めた＝また買った、とみなす |
| ロットの差は控えめ（能力±8、見た目は小さな差） | 空き容器やネットの画像で読んでも大して得しないようにする |
| 用語は品番・ロット・限定パッケージ | ポケモンの種族値・個体値・色違いを避け、商品の言葉に寄せる |
| 画像生成AIを使わない。商品の中身はキーワードの辞書で決める | Warcodes（AIが商品を解釈して能力や画像を作る）と被らない。費用もかからない |
| 商品名・ブランド名は保存も表示もしない | 権利と規約のリスクを避ける。出すのは「ぶどう」などの分類だけ |
| 一度決まった商品の分類は変えない | 調べ先の結果が変わっても、手元のキャラが後から変わらないようにする（2026-11-16 からは D1 に1つだけ残して全員に配る） |
| 収益はB2B（メーカーコラボ、店頭QR、ご当地、受託）。一般向けは無料 | 無料のWeb版で話題を作るほうが先。Steamは保留 |
| 厳選のやり直しを売らない | ガチャ化と規制のリスクを避ける |
| Web版を先にTypeScriptで作る。Flutter Webは使わない | 入口はリンクとQR。開いてすぐ動くのが最優先で、Flutter Webは最初の表示が遅い |
| 配信はCloudflare Workers。Supabaseは使わない | 費用。Supabaseは既に2プロジェクトあり、増やさない |
| 見た目の舞台はスーパーの売り場（値札、レジ、感熱紙） | 題材が商品だから。モンスター図鑑RPGやガチャの見た目に寄せない |
| mainに入れる前にしおみずが確認する | mainは本番にそのまま出るから |
| 方針はチャットで決め、実装は手元（Orca：指示役と実装役）で進める | 2026-11-13〜15 に決定。決まりは `docs/architecture.md` の「進め方」 |
| バトルを「時間で進む＋回す（入れ替え）＋技」に作り直す | 2026-11-12。見ているだけで、戦ってる感がなかった。計画は `docs/battle-plan.md` |
| バトルの計算は別の言語と一致させない | 2026-11-15。相手は常にCPUで、端末どうしで結果を突き合わせる場面がない。完全一致が要るのはキャラ生成だけ |
| 友達テストは「回す」まで作った時点で行う | 2026-11-15。技（必殺）まで作り込んでから「バトルを触らない」と分かるのを避ける |

## 前提：やめたこと・やらないこと

| やめたこと | 理由 |
|---|---|
| バーコードだけで同じ商品の別の1個を見分ける | 13桁が全部同じで、印刷の差もスマホでは拾えない。無理と結論 |
| 「1日1回」の読み取り制限 | 消費サイクルに置き換えた |
| 名前に「バーコードバトル」「バトラー」「〜モン」「Brawl」 | 既存作（バーコードバトラー、Codemon、YOMUMON、Barcode Brawl）と被る。キャラ名にも「モ」を入れていない |
| レア度のガチャ演出 | キングオブバーコードなどと被る。主役は変身 |
| 商品をAIで解釈して能力や画像を作る | Warcodesと被る |
| 刻印ボーナス（賞味期限やロット印字を読む） | 後回し。ドット印字は読み取りが難しく、先に精度の検証が要る |
| 読んだ人に中身をえらんでもらう | 2026-11-16。変身の直前に止めると体験が損なわれる |

## 2026-11-26　試合をゆっくりにして、倍速を付けた（battle-types ブランチ）

しおみずから「流れが速すぎない？妖怪ウォッチ的に倍速を用意すればいい」。妖怪ウォッチも、ふつうの速さで戦い、ボタンで速くできる。

- 決めたこと：1コマを0.1秒→0.2秒にして、攻撃を半分の頻度（6体で1秒に1回ほど）にした。かわりに1発を1.6倍重くし、技のゲージも少し早くたまるようにして、1試合はふつうの速さで1分ほど。「倍速」で今までに近い速さ（30秒ほど）になる
  - 理由：1秒に3回攻撃が飛ぶと、誰が誰に何をしたか追えない。ゆっくりにするだけだと試合が2分近くに延びるので、1発を重くして長さを保った
  - 捨てた案：そのまま全部を半分の速さにする（試合が長くなりすぎる）、攻撃を1つずつ順番に出す（妖怪ウォッチで同時に動くかを確かめられなかった。まずは間隔だけで様子を見る）
- 決めたこと：倍速は押すとすぐ切り替わり、端末に覚える（`barcode-lot:speed`）。最初はふつうの速さ
- 数値は `npm run balance` で、何もしない人43%・技だけ56%・上手い人73%・中央値60秒

## 2026-11-26　手を出せる試合に「からだ」と「あじ」を入れ、先頭をやめた（battle-types ブランチ）

しおみずから「戦いが淡泊。物理と魔法みたいなタイプがほしい。イメージは妖怪ウォッチ」。あわせて「当たる相手は誰でもいい。先頭みたいなシステムはいらない」。

- 決めたこと：能力に**香り**を足す（あじ攻撃の強さ）。品番の乱数の**最後**に引くので、ほかの能力・見た目・名前は変わらない（`golden.json` は香りが増えただけで、ほかの値は前と同じなのを確かめた）
  - 理由：濃さを両方に使うと「型」が生まれない。最後に引けば、今までのキャラはそのまま
  - 捨てた案：濃さを分けて半分ずつ（今の値が変わる）、味で型を決める（同じ味がみんな同じ戦い方になる）
- 決めたこと：攻撃は「からだ」（濃さ）と「あじ」（香り。味ごとの効き目が付く）。濃さと香りの差で「からだ型・あじ型・両方」
  - 理由：あじ攻撃の効き目が、見て分かる変化と「手を出す理由」を作る。味の輪（相性）はそのまま両方に乗る
- 決めたこと：先頭と「前へ」をやめ、操作を**ねらう**（相手をタップ）と**ふく**（味方の効き目を取る。拭いたあと4秒は拭けない）にした。技はそのまま
  - 理由：先頭がないと「前へ」が意味をなくす。代わりに、攻めの操作（ねらう）と守りの操作（ふく）を1つずつ置いた。どちらもタップ1回で、見てすぐ分かる
  - 捨てた案：味方を守る「かばう」（先頭と同じ考え方に戻る）、技の選択（やらないことに入っている）
- 決めたこと：CPUはねらわない（拭く・技は出す）。数値は `npm run balance` で、何もしない人44%・上手い人73%・中央値49秒
- 自動の試合（挑戦状）は前のまま（先頭あり、香りは使わない）。`golden.json` の `battles` も変わらない

## 2026-11-26　ブランチの作業を main に入れた。3Dは最初は2Dで開く

- **battle-feel-port（手応え・ため）と battle-3d（3Dの舞台）を main に入れた**
  理由：しおみずの依頼（「今やるべきこと」の1.）。ブランチに置いたままでは本番で確かめられない。
- **3Dの舞台は、最初は2Dで開き、試合の上の「3Dで見る」を押した端末だけ3Dにする**
  理由：3Dを残すかはしおみずが実機で触って決める。2Dのほうは手応えまで確かめてあるので、それを本番の基本にした。本番のURLのまま、押せば3Dを試せる。
  捨てた案：3Dを基本にして入れる（実機で確かめていない）。3Dを入れずに待つ（確かめる場所がない）。
- **Cloudflare のブランチ用ビルドが通らない原因を、半分まで突き止めた**
  理由：main 以外のブランチだけに push したビルドは、最初の1回から一度も成功していない。手元から同じ `wrangler versions upload` を流すと通るので、コードではなく Cloudflare 側の設定の問題。代わりに `npm run preview:upload` を足した。

## 2026-11-26　3Dの舞台を、重さと重なりを測って直した（battle-3d ブランチ）

実機は使えなかったので、ヘッドレスの Chrome をスマホの大きさ（360×640・390×844・412×915）にし、CPU を4〜6倍遅くして安いスマホの代わりにした。

- **動かない売り場（棚・商品の箱）を2つの部品にまとめ、縞の破片も1つの部品にした**
  理由：箱1つごとに「面」と「黒いふち」を別に描いていて、1コマに描く回数が200〜250回あった。まとめて24〜25回になった（ふつうの速さで 1秒28コマ → 55コマ。ヘッドレスは3Dを CPU で描くので、数字は目安）。
- **画面の細かさは最大1.5倍。1コマ45ms以上が続いたら1倍に下げる。ゆらゆらしているだけの間は1つおきに描く。試合が終わって落ち着いたら描くのを止める**
  理由：安いスマホの電池と熱。2倍だと描く点の数が1.8倍になる。
- **相手まで走り込むのは先頭だけ。後ろの2体は短く踏み込む（援護）**
  理由：メモの「こちらが相手の先頭に重なる」の正体は、攻撃のたびに3体とも相手の先頭めがけて走り、真ん中で3〜4体が団子になることだった。止まっている間は重なっていなかった。
  捨てた案：後ろの2体の攻撃をなくす（計画の「後ろの攻撃の強さ」はしおみずの確認待ちなので、数字は変えない）。
- **こちらの後ろの2体が左右からはみ出さないよう、画面の縦横比からカメラの広さを計算する。後ろの2体は少し内側・少し小さく（0.84倍）**
  理由：縦長の画面で、後ろの2体が左右に30pxずつ切れていた。また、カメラに近いぶん先頭より大きく見えて、先頭を隠していた。3つの画面の大きさで、はみ出しなし・相手が隠れるのは0%になった。

## 2026-11-18　バトルの舞台を three.js で描くお試し（battle-3d ブランチ）

- **舞台と演出だけ3Dにし、キャラは今のSVGの絵をシールにして立たせる**
  理由：しおみずが「three.js でいい感じにしたい。Blenderは重い」。キャラを立体にすると可愛さの調整に時間がかかり、変身演出も作り直しになる。シールなら見た目の方向（値札・ステッカー）とも合い、キャラ生成と golden.json に触れない。
  捨てた案：キャラも3Dにする（品番から立体を組む）。舞台や小物を Blender で作って読み込む（作るのが重い）。
- **舞台も小物もコードで組む（外部の3Dファイルなし）。three.js はバトル画面を開いたときだけ読む**
  理由：入口はQRとリンクで、最初の表示を重くしたくない。three.js は圧縮後およそ136KB で、別ファイルに分けた。依存パッケージ（three）を足すのは、しおみずが three.js を使う案に乗ったので足した。
- **計算（core/live.ts）は変えず、battle-live.ts が出来事を 2D か 3D のどちらかに渡す**
  理由：見た目の差し替えで試合が変わらないようにする。2Dと見比べられるよう、試合の上に切り替えを置いた。

## 2026-11-16　中身の分からない商品は、メーカー番号から推測する

- **JANの頭の番号（メーカーごとの番号）から味を推測する。表は Open Food Facts のデータから自動で作る（`scripts/makers.ts` → `worker/makers.ts`）**
  理由：聞かずに中身の分かる商品を増やすため。外部サービスの許可が要らない。Open Food Facts のデータの書き出しには日本の番号の商品が約4万9千件あり、そのうち約2万件は辞書で味が分かる。それを番号ごとに数えて、同じ味にそろっている番号だけを表にした。
  捨てた案：表を手で作る（どの会社が何を作っているかの確かめが追いつかない）。Open Food Facts の検索APIで集める（日本の番号が少ししか取れず、相手にも負担。書き出しを使うよう案内されている）。

- **表に入れる条件は「同じ味4件以上・70%以上」にした**
  理由：条件を変えて測った（Open Food Facts の中で5つに分けて確かめた当たり／前に集めた別の店の60件のうち、Open Food Facts に無い53件で推測できた数）。
  - 5件・85%：163社。当たり86%（味の系統まで92%）。53件中4件
  - **4件・70%：370社。当たり75%（系統85%）。53件中14件（13件中13件が当たり）**
  - 3件・60%：791社。当たり66%（系統79%）。53件中24件
  大手の多くはお茶・コーヒー・炭酸などを混ぜて作っているので、どの条件でも表に入らない（伊藤園・サントリー・コカ・コーラ・キリンなど）。別の店の60件では、中身が分かる商品が 7件（12%）→ 約21件（35%）になる。
  捨てた案：もっとゆるくする（外れが3件に1件に近づく）。

- **推測した中身は、値札で言い切らない（「コーヒーっぽい商品から生まれた」）**
  理由：4件に1件ほど外れるので、言い切ると嘘になる。

- **この表は ODbL で扱う**
  理由：Open Food Facts のデータ（ODbL）から作ったデータベースなので、同じ条件で扱う必要がある。クレジットは「読む」画面にすでにある。

## 2026-11-16　「中身は何？」と聞くのをやめた

- **読んだ人に中身を聞かない。分からなければ「中身なし」（品番だけで決まる姿）で生まれる**
  理由：人から「体験が損なわれる」と言われた。読んだ瞬間に変身が始まるのがこのゲームの気持ちよさで、企画の「一点」も中身ではなく「縞がそのまま体になる変身」。その直前に質問で止めるのは損。
  捨てた案：はじめて読んだ人に聞く（下の記録。作って試したが外した）。生まれたあとで聞く（中身が決まると姿が変わってしまう）。

- **「中身なし」も答えとしてサーバーに残す**
  理由：「同じ品番なら、どの端末でも同じ姿」を守るため。あとで Open Food Facts に載っても、その品番の姿は変わらない。中身の分かる商品を増やす工夫（メーカー番号からの推測、GS1 Japan のデータ、メーカーとの連携）は、まだ読まれていない品番にだけ効く。

## 2026-11-16　品番の中身は、はじめて読んだ人がえらび、サーバーに1つだけ残す（→ 同じ日に「聞く」部分はやめた。上の記録）

- **Yahoo!ショッピングのAPIは、Yahoo!に確かめるまで使わない。コードからも外した**
  理由：商品検索APIのページが、利用約款として「Yahoo!ショッピング出店API 利用約款」を指している。その約款は、使い道を「お客さんが Yahoo!ショッピングを利用できるようにするサービス」に限り（第4条・第6条）、受け取った情報を保持しないことになっている（第10条）。LINEヤフー共通利用規約も、データを提供目的を超えて使うことを禁じ（第1章 第14条）、APIは原則として非商用に限られる。味を決めるためだけに使い、品番ごとの味を残し、のちにB2Bで収益を得るこの企画は、どれにも引っかかりうる。約款の定義（第2条）には商品検索が入っておらず、どこまでかかるかもはっきりしない。法律の専門家の判断ではない。鍵は未設定だったので、実際に使ったことはない。
  使うなら：お問い合わせ窓口で「JANから分類を作って品番ごとに残してよいか」「商用で使えるか」を書面で確かめる。使える場合もクレジット表示（「Webサービス by Yahoo! JAPAN」）が要る。
  捨てた案：確かめずに使う。商品へのリンクを出して目的に合わせる（世界観が通販になる）。

- **Open Food Facts で分からない商品は、はじめて読んだ人に中身をえらんでもらい、D1 に1つだけ残して全員に配る**
  理由：日本の商品は Open Food Facts にほとんど載っていない（60件中7件）。人にえらんでもらえば、どの商品にも中身が付く。サーバーに1つだけ残すので「同じ品番なら、どの端末でも同じ姿」も守れる（前は通信の具合で端末ごとに違うことがあった）。「この商品の子を最初に決めた」という遊びにもなる。
  捨てた案：品番だけで決まる姿のまま（売りが弱い）。端末ごとにえらぶ（端末で姿が違ってしまう）。多数決（人が少ないうちは決まらない）。

- **先に決まったものが勝つ。あとから変えられない**
  理由：姿が後から変わらないことを優先した。いたずらで違う中身を付けられる心配は残る（`ideas.md`）。

- **「やめる」をえらんだら、生まれない**
  理由：中身なしで生ませると、あとで決まったときに姿が変わってしまう。

- **数字を打って生んだ子には「手入力」の印を付ける**
  理由：強い品番を打ち込むだけで手に入ると、集める価値と対戦の公平さが崩れる。今は印だけで、オンライン対戦に出せなくするのは対戦を作るとき。読めない商品を手で打つ人もいるので、生ませないことはしない。

## 2026-11-16　中身が当たる率を測って、辞書と商品APIを直した

- **商品APIは、調べ先の混雑・障害を「見つからない」と分けて返す（503、キャッシュしない）**
  理由：測っている最中に Open Food Facts が「混んでいる」(429) を返し、今のしくみだとそれが「中身は不明」として30日残り、端末にも保存されることを確かめた。一度そうなると、その品番はずっと味なしの姿になる。
  捨てた案：失敗も `none` のまま、キャッシュだけ短くする（端末側には残ってしまう）。

- **辞書の英語は、単語として出たときだけ当てる**
  理由：Open Food Facts のカテゴリ（en:hot-beverages など）の hot に当たって、おーいお茶が「激辛」になっていた。同じ理由で chocolate の中の cola、legumes の中の ume にも当たりうる。
  捨てた案：まぎらわしい言葉を1つずつ消す（英語のカテゴリは数が多く、追いきれない）。

- **「茶」「水」の1文字は、ほかに当たらないときだけ見る**
  理由：生茶・茶の間のような商品名を拾いたいが、「清涼飲料水」の水などにも出てくるので、先に当てると誤る。

## 2026-11-16　手を出せるバトル（オンライン対戦の土台）

- **今日の挑戦者との試合を、リアルタイムで手を出せる形にした**
  理由：オンラインで同時に戦いたい（自動で進む戦いにその場で手を出す型）という希望。今までの試合は始まる前に結果が決まっていて、同期しても2人で同じ録画を見るだけになる。先に1人用で面白いかを確かめる。
  捨てた案：自動の試合のまま同期する。

- **操作は2つ（前へ・技）。回復は「控えにいると少しずつ」にした**
  理由：最初は3つ目の操作（おかわり）を考えたが、スマホで3体×3ボタンは多い。回復を入れ替えの結果にすれば、ボタンを増やさずに「下げて休ませる」判断が生まれる。
  捨てた案：回復ボタンを別に置く。

- **3体とも攻撃し、当たるのは相手の先頭だけ**
  理由：にぎやかに動き続ける。先頭を誰にするか（受ける役）が、入れ替えの意味になる。
  捨てた案：先頭同士の1対1（静かで読みやすいが、控えがただ待つだけになる）。

- **挑戦状は、今までの自動の試合のまま残した**
  理由：「誰が開いても同じ試合になる」は、手を出せる試合とは両立しない。URLだけで成り立つ今の遊びを壊さない。答え合わせ（`golden.json`）も変わらない。

- **計算は `core/live.ts` に置き、1コマずつ進める形にした**
  理由：画面にも通信にも触れないので、オンラインではサーバー（Durable Objects）で同じ計算を回せる。CPUの操作も人と同じ「操作」の形で足しているので、相手を人に差し替えやすい。

- **CPUは人より少し遅く考える（技は満タンから1.5〜4.5秒後、入れ替えの見直しは2.5〜4.5秒おき）**
  理由：数百試合まわした目安で、何もしないと勝率1%、技だけ即打ちで14%、入れ替えも使うと65%。手を出すほど勝てる。数値（`LIVE`）は遊んでみて直す前提。

## 2026-11-15　構成の整理と画面の作り直し

- **`src/` を層のフォルダに分けた（core / art / store / device / ui）**
  理由：`core` が「Flutter版に移す範囲」と「Workerが読む範囲」をそのまま表すようにするため。向きは `tests/layers.test.ts` で確かめる。
  捨てた案：平置きのまま（`main.ts` に読み取り・値札・棚・画像・試作用の操作が全部入っていて、どこを触ればよいか分かりにくかった）。

- **フレームワークは入れない。画面は「HTMLを描く関数」＋小さなルーター**
  理由：画面は6つで、状態はほぼ端末の記録だけ。開くたびに記録から描き直せば足りる。配信する量も増えない。
  捨てた案：React / Preact / Lit（今の大きさでは得るものより覚えることが多い）。

- **画面はURLの `#` で切り替える（`#/shelf` など）**
  理由：ブラウザの「戻る」が効く。値札やバトルを直接開ける。配信側の設定がいらない（`base: "./"` のまま、どこに置いても動く）。
  捨てた案：`body[data-view]` の出し分けだけ（「戻る」でアプリから出てしまう）、History API のパス（置き場所ごとに設定が要る）。

- **下に3つのタブ（読む・棚・バトル）**
  理由：やることが3つあり、どれも同じ重さ。前は1枚の長い画面で、棚とバトルの入口がスキャナの下に埋もれていた。
  捨てた案：ホーム1枚に全部（今まで）、上のメニュー（片手で届きにくい）。

- **棚は品番ごとに1体。ロットは値札の画面で切り替える**
  理由：同じ品番のロットは姿がほぼ同じで、並べると棚が同じ顔で埋まる。「×2」の札と「入荷あり」で、品番とロットの違いが伝わる。
  捨てた案：ロットごとに全部並べる（今まで。最大40体まで）。チーム選びは能力が違うので、今までどおりロットごとに並べる。

- **今日の挑戦者との結果を端末に残す（`barcode-lot:daily:v1`）**
  理由：「今日はもう挑んだか」が分かり、下のタブの印を消せる。一度勝った日は勝ちのまま。
  捨てた案：残さない（毎日の区切りが見えない）。

- **届いた挑戦状は、タブを閉じるまで持つ（sessionStorage）**
  理由：前は読み込み直すと消えた。棚が空の人は1体生んでから受けるので、その間に消えると困る。
  捨てた案：localStorage にずっと残す（古い挑戦状がいつまでも出る）。

- **「今日の挑戦者」の日付は、アプリ内の時刻で決める**
  理由：試作用の「時間を1日すすめる」で、ロットの入荷と一緒に相手も入れ替わり、確かめやすい。ふだんの動きは変わらない。

- **`#debug` は付けて開いたら、タブを閉じるまで有効**
  理由：`#` を画面の切り替えに使うようにしたので、付けっぱなしにできない。入口（`#debug` を付けて開く）は前と同じ。

- **試合の結果から「挑戦状を送る」を出し、チーム選びの画面からは外した**
  理由：チーム選びの下には決定ボタンを1つだけにしたい。送るだけのときは「バトル」に専用の入口がある。
