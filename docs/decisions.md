# 決めたことと、その理由

しおみずとの相談で決まったこと・やめたこと・まだ決めていないことの記録。
コードを読んでも分からない「なぜ」を置く場所。新しく決まったら、日付つきで足す。企画の全体は `docs/brief.md`。

## しおみずが大事にしていること

- **一番熱いのは、バーコードを読むところと、それが可愛い・かっこいいキャラになるところ**。ここが主役で、ほかは脇
- 同じ商品でも1体ずつ違ってほしい。厳選が楽しいし、コラボもしやすいから
- 読むのはバーコードだけにしたい（レシートや別の撮影を必須にしない）
- バトルは妖怪ウォッチのように「実際に戦ってる感」がほしい。見ているだけは物足りない
- 既存作のパクリと言われたくない
- 開発と運用の費用はできるだけ抑える
- 進め方：先に構成と手順を決めてリポジトリに置き、それを元にエージェントに進めさせる。細かい確認で止まらず、ある程度は自走してほしい

## 決めたこと

| 決めたこと | 理由 |
|---|---|
| 一点は「読んだバーコードの縞がそのままキャラの体になる変身」 | 調べた既存作は「数字→強さ」「1コード→1キャラ」が中心。縞を見た目に使うことで差をつける |
| 品番で姿・名前が全国共通に決まる | 「この商品こいつなの！？」を友達と共有できる。メーカーコラボで「この商品のキャラ」と言える |
| ロットは消費サイクル方式 | バーコードだけでは同じ商品の別の1個を見分けられない。日数を空けて読めた＝また買った、とみなす |
| ロットの差は控えめ（能力±8、見た目は小さな差） | 空き容器やネットの画像で読んでも大して得しないようにする |
| 用語は品番・ロット・限定パッケージ | ポケモンの種族値・個体値・色違いを避け、商品の言葉に寄せる |
| 画像生成AIを使わない。商品の中身はキーワードの辞書で決める | Warcodes（AIが商品を解釈して能力や画像を作る）と被らない。費用もかからない |
| 商品名・ブランド名は保存も表示もしない | 権利と規約のリスクを避ける。出すのは「ぶどう」などの分類だけ |
| 一度決まった商品の分類は端末に保存する | 調べ先の結果が変わっても、手元のキャラが後から変わらないようにする |
| 収益はB2B（メーカーコラボ、店頭QR、ご当地、受託）。一般向けは無料 | 無料のWeb版で話題を作るほうが先。Steamは保留 |
| 厳選のやり直しを売らない | ガチャ化と規制のリスクを避ける |
| Web版を先にTypeScriptで作る。Flutter Webは使わない | 入口はリンクとQR。開いてすぐ動くのが最優先で、Flutter Webは最初の表示が遅い |
| 配信はCloudflare Workers。Supabaseは使わない | 費用。Supabaseは既に2プロジェクトあり、増やさない |
| 見た目の舞台はスーパーの売り場（値札、レジ、感熱紙） | 題材が商品だから。モンスター図鑑RPGやガチャの見た目に寄せない |
| mainに入れる前にしおみずが確認する | mainは本番にそのまま出るから |
| 方針はチャットで決め、実装は手元（Orca：指示役と実装役）で進める | 2026-11-13〜15 に決定。決まりは `docs/architecture.md` |
| バトルを「時間で進む＋回す＋必殺技」に作り直す | 2026-11-12。見ているだけで、戦ってる感がなかった。計画は `docs/battle-plan.md` |
| バトルの計算は別の言語と一致させない | 2026-11-15。相手は常にCPUで、端末どうしで結果を突き合わせる場面がない。完全一致が要るのはキャラ生成だけ |
| 友達テストは「回す」まで作った時点で行う | 2026-11-15。必殺技まで作ってから「バトルを触らない」と分かるのを避ける |

## やめたこと・やらないこと

| やめたこと | 理由 |
|---|---|
| バーコードだけで同じ商品の別の1個を見分ける | 13桁が全部同じで、印刷の差もスマホでは拾えない。無理と結論 |
| 「1日1回」の読み取り制限 | 消費サイクルに置き換えた |
| 名前に「バーコードバトル」「バトラー」「〜モン」「Brawl」 | 既存作（バーコードバトラー、Codemon、YOMUMON、Barcode Brawl）と被る。キャラ名にも「モ」を入れていない |
| レア度のガチャ演出 | キングオブバーコードなどと被る。主役は変身 |
| 商品をAIで解釈して能力や画像を作る | Warcodesと被る |
| 刻印ボーナス（賞味期限やロット印字を読む） | 後回し。ドット印字は読み取りが難しく、先に精度の検証が要る |
| 挑戦状で、送った本人の操作を再現する | 案。相手チームをCPUが動かすだけにする（★確認待ち） |

## 試して分かったこと

- 2026-11：ウェルチ（ぶどうジュース）で1回試して、しおみずの反応は「楽しい」。このとき味が「からい」と出た。商品の中身を辞書で反映する仕組みを入れて修正済み
- 試作はひと通り動くが、しおみずの感覚では「アプリとしての完成度がまだ足りない」（2026-11-12）
- 実機での通しのテストと友達テストは、まだしていない

## まだ決めていないこと

- **タイトル**。仮称は「バーコードの子」。候補はカゴバト／ヨミアワセ／レジ前バトル。決める前に商標検索（J-PlatPat）
- **バトルの3点**（`battle-plan.md` の★）：後衛の援護を威力50%にするか、後衛で回復させるか、挑戦状の相手はCPUでよいか
- **アプリ版の作り方**。今の方針はFlutterで作り直す。バトルと演出がTypeScriptに積もるほど重くなるので、友達テストのあとに「作り直す」か「Web版をアプリの殻で包む」かを決め直す
- **本番のキャラの絵を誰が描くか**（チーム内か外注か）
- Yahoo!ショッピングのClient IDを取るか。ゲーム用途で規約上使えるかの確認も要る
- 友達テストのあとの優先順位：キャラの絵の質、UIの組み直し（開いたら即カメラ全画面、タブ、出会いの瞬間、能力値を奥にしまう）、発見ゲーム

## 友達テストで見ること

1. 2個目を自分から読むか
2. 画像や挑戦状を送るか
3. バトルで「回す」を自分で見つけるか

何も説明せずにURLだけ渡し、口を出さずに見る。
